# /add-portal - Сгенерировать навык поиска по сайту вакансий своего рынка

Ты помогаешь пользователю сделать навык поиска вакансий по сайту вакансий его рынка. В репозитории есть готовые образцы этого шаблона (`habr-search` для Хабр Карьеры и не привязанный к стране `freehire-search`), а README приглашает строить аналоги для других площадок — эта команда превращает приглашение в пошаговый процесс: исследовать портал, собрать навык по канонической структуре и прогнать живой запрос до того, как что-либо регистрировать.

Генератор **не привязан к стране**: он работает для любого портала на любом рынке и языке. Навыки, которые он создаёт, обычно привязаны к рынку и живут в форке пользователя (по правилам репозитория навыки под конкретные страны не принимаются в основной репозиторий (upstream) — генератор и есть функция основного репозитория, а его результат - твой).

Общайся с пользователем по-русски. `$ARGUMENTS` может содержать подкоманду, URL портала или ничего.

Выполняй шаги **строго по порядку**.

---

## Шаг 0: Разбор аргументов

- Если в `$ARGUMENTS` есть `--list`: найди через Glob `.agents/skills/*/SKILL.md`, выведи таблицу установленных навыков-порталов (имя, рынок из описания, источник данных из `url-reference.md`) и остановись.
- Если в `$ARGUMENTS` есть URL: считай его URL портала и передай в Шаг 1.
- Иначе: начни опрос с Шага 1.

---

## Шаг 1: Опрос - основное о портале

Спроси пользователя (пропусти то, на что уже ответил `$ARGUMENTS`):

1. **URL портала** - публичный сайт вакансий (например `https://www.superjob.ru`, `https://getmatch.ru`).
2. **Имя навыка** - kebab-case с суффиксом `-search` (например `superjob-search`, `getmatch-search`). Не должно совпадать с существующей папкой в `.agents/skills/`.
3. **Рынок и язык** - какую страну/регион покрывает портал и на каком языке там вакансии. От этого зависят триггер-фразы в `SKILL.md` (добавляй фразы на местном языке, как это сделано в `habr-search`: «вакансии», «поиск работы», «найди вакансии на …»).
4. **Реалистичный тестовый запрос** - должность или навык, которые пользователь действительно стал бы искать; нужен для живой проверки в Шаге 4.

---

## Шаг 2: Исследуй портал

Сначала разведка, потом код. Используй WebFetch (или `python3 tools/fetch_page.py '<URL>' --text` через Bash, если WebFetch отказывает) на портале:

1. **Найди шаблон URL поиска.** Открой страницу поиска, выполни поиск мысленно в адресной строке или через загрузку и определи: адрес поиска, параметр запроса и параметры для города, возраста вакансии и пагинации. Предпочитай JSON API, если он стоит за сайтом (поищи XHR-адреса `/api/` в исходнике страницы, как у `habr-search` и `freehire-search`), или JSON, встроенный в саму страницу (как в карточке вакансии `habr-search`); иначе планируй разбирать HTML страницы результатов.
2. **Загрузи один ответ поиска** по тестовому запросу и найди поля каждого результата: **id, title, company, location, дату публикации и URL**. Для HTML запиши имена классов / атрибуты, к которым привязано каждое поле. Для JSON запиши пути к полям.
3. **Найди шаблон страницы вакансии** - URL, который отдаёт полное описание одной вакансии, и где в нём лежат описание, дедлайн, тип занятости и ссылка на отклик.
4. **Проверь требования к доступу и условия использования.**
   - Загрузи `robots.txt` и проверь, не запрещены ли пути поиска/вакансии.
   - Если портал требует входа/авторизации для просмотра вакансий, **остановись**: этот шаблон работает только с публичными страницами. Скажи об этом пользователю и предложи проверить, нет ли у портала официального API. (Так, у hh.ru с апреля 2026 публичный API поиска закрыт, а `robots.txt` запрещает поиск с параметрами - поэтому модуля поиска по hh.ru нет.)
   - Если `robots.txt` запрещает эти пути или условия портала запрещают автоматический доступ, прямо скажи об этом пользователю и дай ему решить, продолжать ли для личного использования. Если он продолжает, в сгенерированном `SKILL.md` **обязательно** должен быть заметный раздел «⚠️ Только для личного использования»: держи объём запросов низким, никакого коммерческого или массового использования, ответственность на пользователе.

5. **Проверь, доступен ли портал без учётных данных.** Некоторые порталы отдают пригодное содержимое только через сторонний сервис загрузки (платный API-«разблокировщик»/прокси) или только по ключу API (как SuperJob). **Этот пункт никогда не отменяет Шаг 2.4:** если `robots.txt` или условия портала запрещают доступ, это решено там, и платный сервис загрузки ответа не меняет. Путь с учётными данными существует для порталов, чей `robots.txt` доступ разрешает, но защита от ботов блокирует обычные запросы, или для порталов с официальным API по ключу. Если это так и тестовая загрузка удаётся только через такой сервис или с ключом, скажи об этом пользователю **до генерации** - портал, который берёт деньги за каждый запрос, это совсем другое дело, чем бесплатный, и пользователь может предпочесть его пропустить. Запиши, какой сервис и какая переменная окружения; правила обращения с ними - в контракте навыка-портала в Шаге 3.

Запиши всё найденное - адреса, параметры, привязки полей, особенности - это пойдёт в `url-reference.md` в Шаге 3.

---

## Шаг 3: Сгенерируй навык

**Канонический образец:** перед генерацией прочитай `.agents/skills/habr-search/` (JSON API для поиска + разбор встроенного в страницу JSON для `detail`) и `.agents/skills/freehire-search/` (чистый JSON API) - это рабочие примеры ровно этой структуры с нулевыми зависимостями. Копируй их архитектуру, а не разбор, специфичный для Хабр Карьеры или freehire.

Создай `.agents/skills/<name>/` с:

```
<name>/
├── SKILL.md              # Описание навыка с триггер-фразами
├── url-reference.md      # Документация адресов из Шага 2
└── cli/
    ├── package.json
    ├── tsconfig.json
    ├── README.md
    ├── src/
    │   ├── cli.ts        # Разбор аргументов, справка, выбор команды
    │   ├── helpers.ts    # Загрузка с повторами, парсеры, вывод ошибок
    │   └── commands/
    │       ├── search.ts
    │       └── detail.ts
    └── tests/
        └── helpers.ts    # Утилиты runCLI + parseJSON (скопировать из habr-search)
```

### Контракт навыка-портала (каждый сгенерированный навык ОБЯЗАН его соблюдать)

Эти соглашения делают навыки-порталы взаимозаменяемыми для `/scrape` и для пользователей, читающих документацию любого навыка:

- **Команды:** `search` и `detail <id|url>`.
- **Флаги поиска:** `--query`/`-q`, `--jobage <days>` (возраст вакансии; сопоставь с параметром портала, а если портал его не поддерживает - отметь в SKILL.md или фильтруй на стороне клиента, как `habr-search`), `--page <n>` (с 1), `--limit <n>` (ограничение на стороне клиента), `--format json|table|plain` (по умолчанию `json`). Добавь `--location`/`-l` (или `--city`, как у `habr-search`), если портал поддерживает город как параметр; если город поддерживается только внутри текста запроса, задокументируй это в SKILL.md («включи город в `--query`»).
- **Форма JSON-вывода:** `{ "meta": { "count": ..., "page": ... }, "results": [...] }`, где у каждого результата есть как минимум `id`, `title`, `company`, `location`, `date`, `url` (отсутствующие значения - `null`, никогда не пропускаются).
- **Ошибки:** пишутся в **stderr** как `{ "error": "...", "code": "..." }`, код выхода `1`. Никогда не пиши ошибки в stdout.
- **Загрузка:** честный User-Agent с именем инструмента (`Mozilla/5.0 (compatible; <portal>-cli/1.0)` - соглашение, которому следует каждый поставляемый CLI портала), никогда не полная имитация браузера; если портал отвергает такой UA, переход на браузерные заголовки идёт через проверку `robots.txt` в `.claude/skills/job-application-assistant/09-web-research.md`, а не через поведение CLI по умолчанию. Экспоненциальная задержка со случайным разбросом (jitter) на 429/5xx (максимум ~6 повторов), `""`/`null` на 404 вместо падения.
- **Разбор:** обрабатывай каждый результат (карточку HTML или объект JSON) независимо, чтобы одна битая запись не ломала остальные (см. разбор по карточкам в `habr-search/cli/src/helpers.ts`: `toResult` для каждой вакансии, `parseSsrVacancy`/`parseLdJobPosting` для страницы вакансии). Для HTML режь ответ на куски по одному результату и разбирай каждый отдельно.
- **Зависимости:** по умолчанию **ноль зависимостей во время выполнения** (просто `bun` + `fetch` + разбор регулярками/`JSON.parse`), как у `habr-search` - `bun install` должен тянуть только типы для разработки. Добавляй библиотеку разбора, только если разметка портала действительно не поддаётся разбору регулярками по кускам, и скажи об этом в README.
- **Учётные данные:** навык, которому нужен ключ API (Шаг 2.5), читает его **только** из переменной окружения с именем `<SERVICE>_API_TOKEN`. Никогда не зашивай его в код, никогда не принимай его флагом CLI (флаги утекают в историю оболочки и список процессов) и никогда не пиши настоящий токен в `url-reference.md`, пример в README или тестовые данные. Если переменная не задана, выходи с кодом `1` со стандартной JSON-ошибкой в stderr и кодом `MISSING_CREDENTIALS`, назвав переменную, которую нужно задать, - никогда не проваливайся в неавторизованный запрос, который падает непонятно. Корневой `.gitignore` покрывает `.env`; не коммить его.

### Детали файлов

- **Frontmatter `SKILL.md`:** `name`, `version: 1.0.0`, `description`, написанный для срабатывания навыка, - он должен называть портал, рынок и включать триггер-фразы на английском **и** на языке рынка (для России - на русском); `context: fork`; `allowed-tools: Bash(bun run .agents/skills/<name>/cli/src/cli.ts *)`.
- **Тело `SKILL.md`:** что ищет навык, предупреждение о личном использовании, если Шаг 2 нашёл ограничения в условиях, справочник команд с флагами, 4-6 примеров использования для рынка пользователя (реальные города - для России Москва, Санкт-Петербург, Екатеринбург, Новосибирск, Казань - и реалистичные должности), таблица форматов вывода и раздел Notes с особенностями портала из Шага 2. Если Шаг 2.5 показал, что порталу нужны учётные данные, добавь раздел **Setup** с названием сервиса, точной переменной окружения для `export` и тем фактом, что каждый вызов платный, - там, где пользователь прочитает это до запуска навыка, а не после.
- **`url-reference.md`:** адреса, таблица параметров и заметки о структуре ответа из Шага 2 - это файл, который понадобится будущему сопровождающему, когда портал поменяет разметку.
- **`package.json`:** имя `<portal>-cli`, `"type": "module"`, скрипты `start`, `test` (`bun test --timeout 30000`) и `typecheck` (`tsc --noEmit`); в варианте без зависимостей - только dev-зависимости.
- **`tests/`:** скопируй `runCLI`/`parseJSON` из `habr-search/cli/tests/helpers.ts` (или из `freehire-search/cli/tests/helpers.ts`), затем добавь небольшой живой smoke-тест: `search` с тестовым запросом возвращает код выхода 0 и ≥1 результат с не-null `id`/`title`/`url`; несуществующий флаг или отсутствующий обязательный аргумент даёт выход 1 с JSON-ошибкой в stderr.

## Шаг 4: Прогони живой запрос (ОБЯЗАТЕЛЬНО)

Никогда не регистрируй навык-портал, который не вернул реальных результатов. Допущения о разметке из Шага 2 регулярно упускают особенности, которые видны только вживую.

1. Установи типы для разработки и проверь типы:
   ```bash
   cd .agents/skills/<name>/cli && bun install && bun run typecheck
   ```
2. Запусти живой поиск с тестовым запросом пользователя:
   ```bash
   bun run src/cli.ts search -q "<test query>" --limit 5 --format table
   ```
3. Проверь, что результаты настоящие и полные: должности и компании заполнены (не пустые строки и не обрывки HTML), URL ведут на портал, даты разбираются. Если поля приходят null или искажёнными, исправь парсеры в `helpers.ts` и запусти снова. Повторяй, пока не станет чисто.
4. Возьми один `id` из результатов и запусти `detail`:
   ```bash
   bun run src/cli.ts detail <id> --format plain
   ```
   Проверь, что описание - читаемый текст (сущности раскодированы, теги убраны, абзацы сохранены; кириллица не побита).
5. Запусти тесты: `bun run test`.
6. Держи объём низким во время доработки - несколько запросов, а не обход сайта. Если портал начнёт ограничивать частоту посреди проверки, сбавь темп и скажи пользователю.

Не переходи к Шагу 5, пока search, detail и тесты не пройдут.

## Шаг 5: Регистрация

1. Спроси, хочет ли пользователь добавить новый портал в стратегию поиска `/scrape`. Если да:
   - Сам CLI портала `/scrape` подхватывает автоматически (он находит `.agents/skills/*/SKILL.md`) — для search/detail через CLI больше ничего подключать не нужно.
   - **Предварительное разрешение - отдельно для каждого портала и осознанно.** `/scrape` запускает CLI через Bash, а единственные постоянные разрешения - записи для каждого портала в `.claude/settings.json`. Добавь `Bash(bun run .agents/skills/<name>/cli/src/cli.ts:*)` в `permissions.allow` там **и** в `ALLOWED_PERMISSIONS` в `tools/security_guards.py` в том же коммите - проверка валит CI форка на записи в настройках, которой она не знает, и это задуманный шаг ревью. Пока обе записи не на месте, `/scrape` будет спрашивать разрешение на каждый вызов CLI этого портала; собственная строка `allowed-tools` в сгенерированном `SKILL.md` покрывает только ходы, где навык вызывается напрямую.
   - По желанию добавь в `.claude/skills/job-scraper/search-queries.md` запросы-заготовки для WebSearch/`site:` по этому сайту (в стиле уже имеющихся плейсхолдеров `[YOUR_JOB_BOARD]`), чтобы запасной путь покрывал сайт, если CLI недоступен.
2. Напомни пользователю добавить строку установки для себя, если он ведёт README форка:
   ```bash
   cd .agents/skills/<name>/cli && bun install && cd ../../../..
   ```
   (Можно пропустить, если навык без зависимостей и типы для typecheck не нужны.)
3. Отметь, что навык срабатывает сам по описанию в своём `SKILL.md` - больше ничего подключать не нужно.
4. Покрытие CI тоже автоматическое: задача `cli-checks` находит каждый `.agents/skills/*/cli/package.json`, так что скрипты `typecheck` и `test` нового CLI запускаются при каждом push в форк без правки workflow.

## Принципы

- Генератор не привязан к стране; его результат привязан к рынку и остаётся в форке пользователя. Это соответствует правилу, что основной репозиторий остаётся универсальным шаблоном.
- Сначала исследование, потом генерация: команда никогда не пишет парсеры по догадкам - Шаг 2 сначала загружает реальные ответы, а Шаг 4 проверяет на живых данных до любой регистрации.
- Контракт навыка-портала делает каждый сгенерированный навык взаимозаменяемым с поставляемыми: те же команды, те же флаги, та же форма вывода, то же соглашение об ошибках.
- По умолчанию ноль зависимостей во время выполнения, как у `habr-search`, - навык-портал должен работать на свежем клоне, где нет ничего, кроме `bun`.
- Правила доступа показываются, а не обходятся молча: порталы за авторизацией отклоняются, ограничения `robots.txt`/условий использования сообщаются пользователю, а ограниченные порталы получают в навыке заметное предупреждение «только для личного использования».
- Учётные данные живут в окружении, никогда в репозитории: сгенерированный навык читает токен из переменной окружения, громко падает, если она не задана, и никогда его не коммитит. Стоимость вызова раскрывается до генерации навыка, а не обнаруживается потом.
- Следующие кандидаты для российского рынка - SuperJob (официальный API по ключу) и Getmatch; модулей для них пока нет, их можно собрать этой командой.
